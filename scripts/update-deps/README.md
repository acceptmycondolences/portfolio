# Обновление зависимостей

Запускай обновление только через `pnpm deps:update`, а не вручную через `pnpm update --latest`. Перед запуском или изменением скрипта прочитай это руководство.

## Устройство

`main.ts` задаёт порядок команд, `plan.ts` содержит чистую логику решений, `lock.ts` защищает от одновременных запусков, а `recovery.ts` отвечает за возврат файлов и повторную установку зависимостей. Поведение проверяют `plan.test.ts`, `lock.test.ts`, `recovery.test.ts` и `main.test.ts`; меняя логику, дополняй соответствующие тесты. Node.js 24 выполняет скрипт без сборки, типы проверяет `tsc` по `tsconfig.node.json`.

`main.test.ts` запускает настоящий скрипт в отдельном процессе и временном проекте. `testing/commands.js` подменяет внешние команды и перехватывает запрос к nodejs.org через MSW; файлы, снимки, блокировка и восстановление выполняются настоящим кодом. Тесты не обновляют зависимости рабочего проекта. Процент `pnpm test:coverage` относится только к `src`; дочерние процессы этих интеграционных тестов в него не входят.

## Порядок обновления

- Пакеты, которые создаёт `pnpm create vite` с шаблоном `react-ts` (`react`, `react-dom`, `@types/*`, `@vitejs/plugin-react`, `typescript`, `vite`), получают диапазоны версий из проекта, только что созданного официальным CLI (`pnpm create vite@latest app --template react-ts --no-interactive --no-immediate`), а не latest из реестра. В lock-файле они обновляются только в пределах этих диапазонов. Поэтому `typescript` и `@types/node` остаются на версиях из шаблона, даже если в реестре есть более новые мажорные версии.
- Пакеты шаблона, которых нет в проекте (`oxlint` — проект использует ESLint), не добавляются.
- `@types/node`, если его нет в шаблоне, получает мажорную версию из `.nvmrc` (`^24.0.0`), а не latest: типы должны соответствовать Node.js проекта. Если он есть в шаблоне, диапазон шаблона важнее.
- Если в реестре есть версия закреплённого пакета вне его диапазона (например, TypeScript новее, чем в шаблоне), скрипт сообщает об этом в разделе «Для справки», но не обновляет пакет и не меняет код завершения.
- Остальные пакеты сначала обновляются в пределах своих диапазонов. pnpm (`packageManager`) обновляется на этом этапе только тогда, когда его latest остаётся в той же мажорной версии; если latest уже следующего мажора, скрипт позже пробует сразу его, не подбирая последний релиз старого мажора. Если после первого этапа не проходят проверки, скрипт пытается откатить изменения и завершается с ошибкой.
- Затем пробуются обновления до latest за пределами текущих диапазонов — только для пакетов, текущая версия которых ниже latest: пре-релиз новее latest (`6.0.0-beta` при latest `5.4.0`) не понижается. Код `pnpm outdated` 1 допустим только вместе с непустым JSON-результатом; пустой вывод при ошибке или другой ненулевой код запускает откат. Сначала все вместе (если групп больше одной), при неудаче — группами, при неудаче группы — по одному. Группа — пакеты одного семейства (`vitest` и `@vitest/*`, `eslint` и `@eslint/*`) или одной линейки выпусков (одинаковые текущая и новая версии: `eslint-plugin-react-x` и `eslint-plugin-react-dom`). Каждое обновление остаётся, только если проходят проверки.
- После пакетов пробуются новая мажорная версия pnpm и новая мажорная LTS-версия Node.js (с nodejs.org: `.nvmrc` и `engines.node`). Node.js обновляется, только если pnpm действительно находит новую версию по `.nvmrc` (`pnpm exec node --version`): `pnpm install` и `pnpm check` без неё не падают, а выполняются на текущей. Версию Node.js скрипт не устанавливает.

## Проверка и восстановление

- Проверка — `pnpm check` и `vite build` во временный каталог (`dist` не меняется). Упавшая проверка повторяется один раз: browser-тест может упасть из-за перезагрузки Vite после новой зависимости (см. раздел «Тесты» в `CLAUDE.md`). Неудовлетворённые peer-зависимости проверки не ловят: после обновления просмотри предупреждения pnpm (известные — в разделе «Известные предупреждения» в `CLAUDE.md`).
- В git скрипт отказывается работать, если в `package.json`, `pnpm-lock.yaml` или `.nvmrc` есть незакоммиченные изменения. Файл `node_modules/.tmp/deps-update.lock` не допускает два одновременных запуска; при аварийном завершении убедись, что обновление больше не выполняется, и удали оставшийся файл блокировки перед повторным запуском. Снимок файлов хранится в `node_modules/.tmp/deps-update-backup.json`: при Ctrl+C скрипт пытается откатить изменения всего прогона (включая уже прошедшие мажорные обновления), а после закрытия терминала или сбоя их восстанавливает следующий запуск после удаления оставшейся блокировки. При откате всего прогона резервная копия удаляется только после успешной повторной установки зависимостей; если она не удалась, исправь причину и запусти команду снова. При успешном обновлении копия удаляется после всех проверок. Если между запусками эти файлы меняли вручную, их текущие версии перед восстановлением сохраняются в `node_modules/.tmp/deps-update-replaced.json`.

## Коды завершения

- `0` — обновление завершилось без пунктов «Требует внимания» (в разделе «Для справки» могут оставаться новые версии закреплённых пакетов или патч Node.js).
- `2` — обновление прошло, но в конце перечислено, что требует внимания: мажорная версия ломает проверки, нужно установить новую LTS-версию Node.js или обновить упоминания версий в `CLAUDE.md`, недоступен nodejs.org или реестр при проверке версии pnpm.
- `1` — ошибка; `130` — прервано. Если изменения уже начались, скрипт пытается их откатить. При неудачном восстановлении резервная копия остаётся на диске. Пункты из списка «Требует внимания» решай отдельными задачами.
