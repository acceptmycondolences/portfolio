# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Окружение

- Node.js 24 (`.nvmrc`, `engines`), пакетный менеджер — только pnpm 12 (`packageManager`). `engineStrict` включён: pnpm не установит пакеты, которые заявляют о несовместимости с текущей версией Node.js.
- Тесты — Vitest 5: логика в Node.js, компоненты в Chromium через Browser Mode (Playwright + `vitest-browser-react`). Подробности в разделе «Тесты».

### Когда что запускать

- После изменений кода запускай `pnpm check`; он входит в `pnpm build`. Pre-commit проверяет архитектуру и индексированные файлы, а тесты запускает только для связанных файлов, поэтому не заменяет полный `pnpm check`. Любое предупреждение ESLint считается ошибкой.
- Перед первым сообщением о завершении задачи самостоятельно сверь результат с исходным запросом и просмотри итоговые изменения. Для изменённого поведения проверь применимые сценарии: обычный путь, ошибка, повторный или параллельный вызов, прерывание и восстановление. Учти уже существующие пути выполнения, на которые влияет правка; важные сценарии закрепи тестом или проверь вручную. Прохождение `pnpm check` само по себе не подтверждает сценарии, которых нет в тестах. Если что-то существенное проверить нельзя, прямо укажи это в результате, не ожидая отдельной просьбы о ревизии.
- `pnpm fix` переписывает исходники, поэтому запускай его осознанно и просматривай результат. Не встраивай `fix` в `build` и другие проверочные скрипты: сборка и проверки не должны менять исходники (перегенерация дерева маршрутов — единственное исключение, это сгенерированный файл).

## Обновление зависимостей

Зависимости обновляй только командой `pnpm deps:update`, а не вручную через `pnpm update --latest`. Перед запуском команды или изменением `scripts/update-deps/*` прочитай [руководство по обновлению](scripts/update-deps/README.md): в нём описаны порядок обновления, проверки, восстановление и коды завершения. Меняя логику скрипта, дополняй соответствующие тесты.

## Git-хуки (Husky)

- `pre-commit`: `pnpm arch:check` по всему `src`, затем `pnpm lint-staged --concurrent false` по индексированным файлам. Правила в `lint-staged.config.js`: Prettier для не-JS/TS файлов; для JS/TS сначала Prettier, затем ESLint; для TS ещё `pnpm types:check` по всему проекту, проверка, что дерево маршрутов после генерации совпадает с индексированным (иначе коммит блокируется), и `vitest related --run` — тесты, зависящие от индексированных файлов. Шаблоны выполняются по очереди (`--concurrent false`): по умолчанию lint-staged запускает их параллельно, и `tsc` с Vitest могли бы прочитать TS-файл, пока Prettier его перезаписывает. Шаблоны Prettier не пересекаются, чтобы каждый файл форматировался один раз.
- `commit-msg`: commitlint с `@commitlint/config-conventional`. Формат `type(scope): subject`:
  - `type` — одно из `build`, `chore`, `ci`, `docs`, `feat`, `fix`, `perf`, `refactor`, `revert`, `style`, `test`;
  - `subject` начинается со строчной буквы и не заканчивается точкой;
  - заголовок и строки тела — не длиннее 100 символов.

## Тесты

Тесты в проекте в основном пишет ИИ. Правила ниже основаны на https://vitest.dev/guide/learn/writing-tests-with-ai и https://vitest.dev/guide/browser/.

### Устройство

- Настройки Vitest — в поле `test` файла `vite.config.ts` (отдельного `vitest.config.ts` нет): тесты используют те же плагины и алиас `~/*`, что и приложение. Не создавай `vitest.config.ts` — он заменит настройки из `vite.config.ts`.
- Два проекта Vitest, набор выбирается по имени файла:
  - `unit` — `*.test.{ts,tsx}` в `src` и `*.test.ts` в `scripts`, Node.js без DOM: функции, сторы, мапперы, валидаторы, чистая логика скриптов. Тесты из `src` `tsc` проверяет с типами DOM из `tsconfig.app.json`, поэтому браузерные глобальные объекты (`document`, `window` и т. п.) в них запрещает ESLint (`no-restricted-globals`); тесты из `scripts` проверяются по `tsconfig.node.json`, где типов DOM нет;
  - `browser` — `*.browser.test.{ts,tsx}`, настоящий Chromium через Playwright (Browser Mode): всё, что рендерит React или работает с DOM, включая хуки через `renderHook`.
- Тест лежит рядом с тестируемым файлом: `format.ts` → `format.test.ts`, `Foo.tsx` → `Foo.browser.test.tsx`.
- `vitest.browser.setup.ts` подключает `vitest-browser-react` и стили приложения; он входит в `tsconfig.app.json`. Реальные стили нужны для проверки адаптивной видимости и размеров canvas.
- Моки сбрасываются автоматически (`mockReset`, `restoreMocks`, `unstubEnvs`, `unstubGlobals` в `vite.config.ts`). Перед каждым тестом у всех моков очищается история вызовов и возвращается исходная реализация из фабрики `vi.mock` или `vi.fn(impl)`, поэтому `mockReturnValue` из одного теста не попадает в следующий. После каждого теста восстанавливаются `vi.spyOn`, `vi.stubEnv` и `vi.stubGlobal`. Не дублируй это в `beforeEach`/`afterEach`. Каждый тест, которому нужно особое поведение мока, задаёт его сам.
- Chromium для установленной версии Playwright скачивается командой `pnpm test:browsers`; после обновления Playwright может потребоваться повторная загрузка.
- Браузер в тестах запускается без окна (`headless: true` в `vite.config.ts`). Чтобы видеть его при отладке (человеку, не агенту): `pnpm exec vitest <путь> --browser.headless=false`.
- `coverage/` и `.vitest/` (артефакты Vitest 5, в том числе скриншоты упавших браузерных тестов) — в `.gitignore`.
- Покрытие в `vite.config.ts` считается только по `src`, с исключением тестов, деклараций типов, сгенерированного дерева и файлов объявлений маршрутов из `src/app/routes`. Для всего остального кода в отчёте действуют пороги 100% по statements, branches, functions и lines. Это проверка исполнения кода, а не полноты сценариев и утверждений. Маршруты проверяются через реальный роутер; скрипты из `scripts` участвуют в прогоне тестов, но в эти проценты не входят. Устройство интеграционных тестов обновления описано в [руководстве](scripts/update-deps/README.md).

### Запуск тестов агентом

- Запускай только однократно: `pnpm exec vitest run <путь>` для своих файлов, затем `pnpm check`. Не запускай `pnpm test` (`vitest` без `run`): Vitest отключает режим наблюдения, когда распознаёт агента, но документация называет это распознавание ненадёжным, поэтому на него не полагайся.
- Vitest сам определяет Claude Code (переменная `CLAUDECODE`) и включает компактный репортёр `minimal`: выводятся только упавшие тесты. Поэтому `reporters` в конфиге не задаётся — иначе автоопределение отключится.
- Для подробного вывода по одному файлу: `pnpm exec vitest run <путь> --reporter=verbose`.
- Проверяй код завершения и весь итог прогона: прошедшие тесты и 100% покрытия не означают успех, если Vitest сообщил `Unhandled Errors` или `Unhandled Rejection`.
- Предупреждение `Vite unexpectedly reloaded a test` появляется один раз, когда browser-тест впервые импортирует зависимость, которой ещё нет в кэше Vite. Если тест из-за этого упал, перезапусти его. Не добавляй `optimizeDeps.include` по совету из предупреждения: Vitest сам сканирует тестовые файлы через `optimizeDeps.entries`, и при чистом кэше (в CI) перезагрузки нет.

### Как писать тесты

Пошаговый процесс (контекст → план сценариев → тесты → запуск → ревью → доработка) — в скилле `/write-tests` (`.claude/skills/write-tests/SKILL.md`). Для Codex тот же процесс доступен через `.agents/skills/write-tests/SKILL.md`, который ссылается на этот файл, поэтому правила не дублируются. Используй его для любой задачи на написание или доработку тестов. Правила ниже действуют всегда.

- Контекст до написания: тестируемый файл целиком (с импортами и типами), соседние тесты (следуй их стилю), этот раздел (окружение, глобальные API, setup-файлы) и файлы зависимостей, которые будешь мокать, — хотя бы их типы.
- Только API Vitest, импортированные явно из `vitest` (глобальные API выключены): `vi.fn`, `vi.mock`, `vi.spyOn`. Никаких `jest.*` — их отсутствие ловит `tsc`. При сомнении сверяйся со справочником: https://vitest.dev/api/vi.
- Структура: `describe('<ИмяМодуля>')` на верхнем уровне, при нескольких функциях или методах — вложенный `describe` на каждую. Внутри `it('…')`: короткое описание поведения на русском (`'форматирует сумму в UZS'`, `'бросает ошибку для отрицательной суммы'`), а не длинное «должен корректно вернуть … когда …».
- Общая подготовка данных — фикстурами, а не `beforeEach`: `import { it as baseIt } from 'vitest'`, затем `const it = baseIt.extend<{ … }>({ … })`. Второй параметр функции фикстуры называй `provide`: имя `use` ошибочно распознаётся React-линтерами как хук. Подготовленные ресурсы и изменённое общее состояние освобождай или восстанавливай в `finally`; автоматический сброс моков не очищает файлы и storage.
- Моки модулей — `vi.mock(import('./module'))`, а не строкой: так проверяются путь и типы (https://vitest.dev/guide/learn/mock-functions#mocking-modules). Типизированный доступ к моку — `vi.mocked(fn)`.
- Не перемокивай: тестируй настоящую реализацию модулей проекта. Мокай только внешние границы — сеть, время (`vi.useFakeTimers`), случайность, браузерные API, которые нельзя выполнить в тесте. Не проверяй сам мок вместо поведения.
- Browser-тесты:
  - рендер — `const screen = await render(<Component />)` из `vitest-browser-react`, `render` всегда с `await`;
  - элементы — локаторами по роли и тексту: `screen.getByRole('button', { name: 'Сохранить' })`, `getByLabelText`, `getByText`; `getByTestId` — только если иначе нельзя;
  - действия — методами локатора (`await locator.click()`, `await locator.fill('…')`) или `userEvent` из `vitest/browser`;
  - проверки DOM — `await expect.element(locator).toBeVisible()` и т. п. (повторяются до успеха); обычный `expect` — для значений, не для DOM;
  - `expect(screen.getByRole(...)).toBeTruthy()` и аналогичная проверка `getByText` проверяют объект локатора, а не наличие элемента. Для отсутствия элемента используй `await expect.element(locator).not.toBeInTheDocument()`;
  - адаптивное поведение проверяй через `await page.viewport(width, height)`, чтобы media query и CSS работали с одной шириной. Управляемый `matchMedia` уместен в отдельных тестах хука или reduced motion;
  - `toHaveTextContent` в Vitest 5 сравнивает текст строго; для части текста или регулярного выражения — `toMatchTextContent`;
  - `vi.spyOn` на экспорт модуля в браузере падает — используй `vi.mock(import('./module'), { spy: true })`;
  - экспортированную переменную (`export let`) в браузере подменить нельзя: меняй её через экспортированную функцию модуля или мокай весь модуль через `vi.mock`;
  - `alert`, `confirm` и `print` блокируют страницу, поэтому Vitest заменяет их заглушками по умолчанию. Если код их вызывает, задай поведение явно: `vi.stubGlobal('confirm', vi.fn(() => true))`;
  - не используй `@testing-library/*` и `jsdom`: их нет в проекте, Browser Mode их заменяет.
- Проверяй поведение, а не реализацию (https://vitest.dev/guide/learn/testing-in-practice#what-to-test). Критерий: если внутренности переписать, а результат останется верным, тест не должен упасть. Не проверяй вызовы внутренних функций и их порядок, если результат можно проверить напрямую.
- Утверждения конкретные: `toBe`, `toStrictEqual`, `toMatchObject` + `toBeTypeOf` для сгенерированных полей, `toThrow('сообщение')`. Запрещены `toBeDefined` (ловит ESLint) и проверки «не упало». Для длинных сообщений об ошибках допустим `toMatchInlineSnapshot`; файловые снапшоты не используем.
- Покрывай граничные случаи явно: пустой ввод, `null`/`undefined`, граничные значения, ошибки, упавшие запросы, пустые списки. Однотипные случаи — через `it.for([...])`, а не копированием тестов.
- Исходные данные должны отличаться от ожидаемого результата, когда проверяется изменение: например, включи тени до проверки их отключения. Для независимости ключей storage используй разные значения. Проверяй, что тест обнаруживает удаление или поломку нужного действия, мысленно либо временной мутацией с обязательным восстановлением исходника.
- Маршрутизацию проверяй переходом или загрузкой адреса через настоящий роутер и содержимым нужной страницы. Наличие `Route.options.component` само по себе не подтверждает выбор правильного компонента.
- Асинхронный код — с `async`/`await` и `.resolves`/`.rejects` (`await expect(p).rejects.toThrow('…')`); незаавейченный промис, в том числе `expect.element`, ловит ESLint.
- Сетевые запросы перехватывай через установленный MSW 3, не подменяй `fetch`. HTTP-обработчики и `HttpResponse` импортируются из `msw/http`, `setupServer` для Node.js — из `msw/node`. В тестах скрипта сервер работает внутри дочернего процесса; его настройка показана в `scripts/update-deps/testing/commands.js`. Для browser-тестов API понадобится отдельная настройка MSW в браузере; Node-настройка туда не переносится.
- Данные в тестах — только синтетические.
- Для `*.test.{ts,tsx}` действуют `vitest.configs.recommended` и правила против ошибок ИИ из `eslint.config.js`. Не отключай их через `eslint-disable`.

### Граница проверки сторонней анимации

В тестах маршрутов, композиции и entrypoint внешняя библиотека `typeit-react` изолирована моками. Реальное появление итогового текста проверяет [GreetingSection.browser.test.tsx](src/pages/home/ui/GreetingSection.browser.test.tsx). При прогоне маршрутов с настоящей анимацией и покрытием наблюдались необработанные исключения `insertBefore` внутри библиотеки при быстрой смене страниц. Исправление этой гонки не подтверждено: изоляция анимации в тестах маршрутов не доказывает корректность её быстрого размонтирования. Для исправления нужен отдельный воспроизводимый регрессионный сценарий.

## Сгенерированные файлы

- `src/app/router/generatedRouteTree.ts` генерируется из файлов в `src/app/routes`: Vite-плагином при `pnpm dev`/`vite build` и CLI при `pnpm routes:generate` (входит в `types:check`). Не редактируй его вручную. Он исключён из Prettier и ESLint и хранится в репозитории. Изменённое дерево коммить вместе с маршрутами.
- Пути маршрутов задаются только в `tsr.config.json`, его читают и CLI, и Vite-плагин. JSON без комментариев, поэтому пояснения к нему — в `vite.config.ts` рядом с `tanstackRouter()`.
- `pnpm-lock.yaml` исключён из Prettier: его формат задаёт pnpm.

## Известные предупреждения

Эти предупреждения не влияют на результат и исправляются только в самих пакетах. Не пытайся устранить их понижением версий или правкой конфигов:

- `tsr generate` пишет `Warning: Accessing non-existent property 'replaceRouteChunk'…`;
- pnpm сообщает о неудовлетворённых peer-зависимостях: `eslint-plugin-jsx-a11y` ждёт ESLint ≤ 9, `tsconfck` (через steiger) — TypeScript 5.

## Соглашения в конфигурации

- В `vite.config.ts` сохраняй назначение и приоритеты `build.rolldownOptions.output.codeSplitting.groups`: `react`/`react-dom` выделяются в `react-vendor` (20), `three` — в `three-vendor` (15), остальные зависимости из `node_modules` — в `vendor` (10), а крупные модули, используемые минимум двумя входами сборки, — в `common` (5; минимум 10 КБ). Приоритеты оставляют специализированные группы выше общих. Если меняешь настройки сборки, проверок или инструменты, влияющие на команды и рабочий процесс, обновляй это руководство в том же изменении; документируй значимое поведение и контракты, а не каждую настройку конфига.
- Исключения в `.gitignore`, `.prettierignore` и `globalIgnores` в `eslint.config.js` перечисляй в порядке проводника VS Code сверху вниз: сначала каталоги по имени, затем корневые файлы и маски. В `.gitignore` сохраняй связанные правила вместе и ставь разрешающие правила `!` после соответствующего исключения.
- Алиас `~/*` → `src/*` задан только в `tsconfig.app.json`; Vite читает его через `resolve.tsconfigPaths`. Не дублируй алиас в других конфигах.
- В конфигах, которые поддерживают комментарии, каждая настройка сопровождается комментарием на русском, который объясняет, зачем она нужна. В `package.json`, `tsr.config.json` и `.nvmrc` комментарии невозможны. В `eslint.config.js` пометка «Дополнение:» отмечает то, чего нет в шаблоне Vite. Обычные комментарии ставятся выше JSDoc `@type`, а не между ним и `export default`.
- Порядок импортов задаёт Prettier (`@ianvs/prettier-plugin-sort-imports`, группы по слоям FSD), поэтому правила сортировки импортов в Perfectionist отключены.
- Не добавляй настройки, которые совпадают со значениями по умолчанию (например, `strict` и `module: esnext` в TypeScript 6+). Значения из шаблона Vite в `tsconfig*.json` сохраняются, только если меняют поведение. В `prettier.config.js` сохраняй `'decorators-legacy'` для сортировки импортов.
- В JS/TS-конфигах ключи объектов сортируются по алфавиту, это проверяет Perfectionist. В JSON порядок не проверяется: в `tsconfig*.json` сохранён порядок из шаблона Vite, `scripts` в `package.json` сгруппированы по смыслу, остальные JSON-файлы (`.vscode/*`, `tsr.config.json`) отсортированы по алфавиту.

## Ревизия инструкций для ИИ

- Оценивай инструкции по проверяемым последствиям для работы агента: неверная команда, противоречие, устаревшее утверждение или отсутствующее правило, из-за которого уже возникла конкретная ошибка. Для каждого замечания укажи доказательство и практическое влияние.
- Отделяй подтверждённые проблемы от необязательных улучшений и предположений. Не представляй иной стиль организации документации как исправление ошибки без свидетельств, что текущий подход мешает работе.
- Не называй документацию «идеальной» или «полностью соответствующей лучшим практикам»: успешная проверка показывает только то, что было проверено. При повторной ревизии объясняй изменение оценки новыми фактами или исправлениями; не придумывай новые замечания ради списка.
